# Битрикс24 — ведение базы

Портал ведёт клиентскую базу целиком. Правило простое: **если действия нет в Битриксе, его не было.**

Воронка: **«Прямые покупатели», `CATEGORY_ID = 0`**. Сущность — сделка (`deal`). Лиды в системе есть, но CRM работает в простом режиме и конвертирует их в сделки за секунду — все 42 лида имеют статус `CONVERTED`. С лидами не работаю.

---

## Стадии

| Стадия | Код | Когда перевожу |
|---|---|---|
| Новый лид | `NEW` | Заявка появилась, содержательного ответа клиента ещё нет |
| Квалификация | `PREPARATION` | Клиент ответил, выясняю цель / срок / бюджет / критерий |
| Получен контакт (номер/канал) | `UC_CONTACT` | Клиент дал телефон, MAX или Telegram → **передача Ирику** |
| Встреча назначена | `UC_MEET_SET` | Согласованы дата и формат встречи или созвона |
| Встреча проведена | `UC_MEET_DONE` | Встреча или созвон состоялись |
| Подбор участка | `PREPAYMENT_INVOICE` | Отправлена вилка, обсуждаются конкретные номера участков |
| Прогрев | `EXECUTING` | Клиент взял паузу, веду по цепочке касаний |
| Бронь | `FINAL_INVOICE` | Внесены 30 000 ₽, участок снят с продажи |
| Договор и оплата | `UC_DOGOVOR` | Договор подписан либо выставлен счёт |
| Сделка успешна | `WON` | Оплачено полностью |
| Сделка провалена | `LOSE` | 5 касаний без ответа, отказ, дубль, нецелевой |
| Анализ причины провала | `APOLOGY` | Не использую автоматически — только по указанию Ирика |

**Правило перевода: стадия отражает самое дальнее достигнутое состояние.** Назад двигаю только в двух случаях — сделка провалена или Ирик сказал.

⚠️ **Известная нестыковка порядка.** В Битриксе `UC_CONTACT` (SORT 25) и встречи (26, 28) стоят *перед* «Подбором участка» (30). В переписке порядок обычно обратный: сначала подбираем участок, потом получаем телефон и назначаем встречу. На работу это не влияет, но отчёт по воронке будет выглядеть рвано. Исправляется переустановкой SORT — жду решения Ирика, сам не трогаю.

## Название сделки

Формат: **`Имя ДД.ММ.ГГГГ (Авито)`** — дата первой заявки.

Пометки в названии добавляю через пробел в конце: `ОТКАЗ`, `ДУБЛЬ`. По ним потом фильтруется рассылка — сделки с пометкой `ОТКАЗ` в касания не берутся.

Автосделки от открытой линии приходят с названием `Имя - Открытая линия` — переименовываю в наш формат при первом касании.

## Комментарии в таймлайн

**Каждое отправленное сообщение — в карточку, полным текстом, с пометкой зачем так написано.** Через неделю никто не вспомнит логику, а история переписки — единственное, что позволяет вернуться к клиенту осмысленно.

```
b24_call → crm.timeline.comment.add
  ENTITY_ID: <ID сделки>
  ENTITY_TYPE: "deal"
  COMMENT: <текст>
```

Формат комментария:

```
📤 ОТПРАВЛЕНО 12.08.2026 09:14 · Авито · чат u2i-XXXX
Касание 3 из 5. Повод: запрос техусловий по выбранному участку.

<полный текст сообщения, как ушло>

Логика: клиент упирался в стоимость подключения газа (450к в прошлом
опыте). Не даю цифру без ТУ — даю причину назвать участок.
Следующий шаг: 15.08 вернуться с суммой по ТУ либо касание 4 (срок и деньги).
```

Для входящего — то же самое с 📥 и без блока логики.

**Записываю сразу после отправки, по одному чату.** Батчем в конце прогона — так три комментария уже легли не в те карточки.

## Задачи

Ставлю через `b24_task_add`, ответственный — **ID 1 (Ирик Рафиков)**.

| Повод | Заголовок | Дедлайн |
|---|---|---|
| Клиент дал телефон | `Позвонить: [Имя], [телефон] — Авито, сделка [ID]` | В течение часа |
| Назначена встреча | `Встреча: [Имя], [дата/время], [формат] — сделка [ID]` | За 2 часа до |
| Клиент просит живого человека | `Подключиться в чат: [Имя] — сделка [ID]` | Сегодня |
| Упёрся в стоп-кран | `Решение по [вопрос]: [Имя] — сделка [ID]` | Тот срок, что назван клиенту |
| Клиент готов к брони | `Бронь 30 000 ₽: [Имя], участок №[N] — сделка [ID]` | Сегодня |

В описание задачи — контекст: что клиент хочет, что уже обсуждали, что я ему пообещал и к какому времени.

## Дубли

Открытая линия (конфиг ID 1) создаёт лид на каждое обращение, лид за секунду конвертируется в сделку. Сессия закрывается через 4 часа тишины, окончательно истекает через сутки — клиент, ответивший на следующий день, попадал в новую сессию и плодил новую сделку.

12.08.2026 поставлен `CRM_CREATE_SECOND = N`: если у контакта уже есть сделка, новая сессия привязывается к ней. Полная механика — `база-знаний/ИНТЕГРАЦИЯ-АВИТО-БИТРИКС.md`.

**Остаточный эффект.** У чатов, по которым сделка заводилась через API, на контакте нет IMOL-привязки `imol|avito|1|<chat_id>|<user_id>`. Для открытой линии такой клиент — новый, и при следующем сообщении она создаст **один** лишний дубль. Дальше по этому контакту дублей не будет.

**Как отличить автосделку:**

| Признак | Значение |
|---|---|
| Название | заканчивается на `- Открытая линия` |
| `SOURCE_ID` | `1\|AVITO` |
| `LEAD_ID` | заполнен |
| `CREATED_BY_ID` | `1` |
| У контакта | есть поле IM типа IMOL |

Ни одного из этих признаков нет у сделок, заведённых вручную или через API.

**Что делаю с дублем:** не удаляю. Переношу в исходную сделку всё, чего в ней нет, привязываю контакт к исходной, дубль → `LOSE`, причина `65` (нецелевой), в название дописываю `ДУБЛЬ`.

## Перед созданием сделки

Проверяю, нет ли её уже: `b24_crm_list` по `CATEGORY_ID = 0` с фильтром `%TITLE` по имени и по датам. Заводить вторую карточку тому, кто уже есть в базе, — та же ошибка, что писать одному человеку в два чата.

Если сделку завожу сам (открытая линия не сработала) — по возможности создаю и **контакт** с привязкой к чату. Сделка без контакта не опознаётся открытой линией и станет источником дубля.
